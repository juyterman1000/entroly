# Competitive visibility operating model

Entroly's goal is not to look louder than External Baseline or External Context Tool. The goal is to
be easier to discover, easier to install, easier to evaluate, and harder to
misunderstand than any alternative in the context-engineering category.

This page defines what "stronger visibility" means and prevents the project from
confusing copied listings, inflated claims, or short-lived launch traffic with
real distribution strength.

## The leadership standard

Entroly leads a visibility dimension only when all five conditions hold:

1. **Coverage** — the relevant package, document, integration, catalog, or
   channel exists.
2. **Clarity** — a new user can understand the product and the exact setup path.
3. **Proof** — important claims are linked to executable checks, raw artifacts,
   or an independent public source.
4. **Maintenance** — version, install command, links, and limitations stay
   current after releases.
5. **Outcome** — the surface produces qualified installs, reproductions,
   integrations, or reviews rather than impressions alone.

A directory entry without maintenance is not leadership. A benchmark without a
fair baseline is not leadership. A high compression ratio without task quality
is not leadership.

## What the strongest competitors currently demonstrate

External Baseline's official documentation provides separate pages for MCP, TypeScript,
Vercel AI SDK, framework integrations, proxy use, compression mechanics, and
recovery. External Context Tool's official documentation emphasizes one-command onboarding,
a broad agent matrix, managed Claude instructions and skills, native packages,
and an interactive setup prompt.

Entroly should exceed these patterns by combining their onboarding and discovery
strength with stronger recovery evidence, receipt transparency, fail-closed
verification, neutral benchmark discipline, and release-surface consistency.

## Complete visibility dimensions

The machine-readable source of truth is
[`visibility-dimensions.json`](visibility-dimensions.json). It covers:

- category positioning and repository first impression;
- Python, npm, Rust, Homebrew, Docker, and operating-system packages;
- MCP, Claude plugin, Agent Skills, coding-agent and IDE integrations;
- onboarding, documentation, technical SEO, AEO/GEO, and multilingual reach;
- neutral comparisons, independent reviews, external benchmarks, and raw proof;
- curated lists, launch channels, newsletters, podcasts, and technical media;
- community proof, release communication, citation metadata, and press assets;
- security, privacy, governance, extensions, and distribution observability.

No dimension can silently disappear from the plan merely because it is hard.
Blocked dimensions must state the missing evidence and the next executable step.

## Priority sequence

### Tier 1 — Discovery that converts immediately

- Claude Code, MCP, CLI, local-AI, and agent-infrastructure catalogs.
- Correct package metadata and one-command setup.
- Searchable task-specific documentation and machine-readable direct answers.
- Trust pages that make privacy, proxy behavior, recovery, and limitations clear.

### Tier 2 — Independent credibility

- Hands-on reviews using real repositories and real tasks.
- Version-pinned neutral benchmark adapters.
- Reproducibility reports that include failures and pass-through cases.
- Technical articles explaining the mechanism rather than repeating taglines.

### Tier 3 — Long-tail distribution

- Nix, Scoop, FreeBSD, and additional package collections.
- Maintained multilingual pages and regional MCP/AI directories.
- Research citation metadata, newsletters, podcasts, and conference demos.
- Safe extension and addon discovery.

## Scoreboard rules

Track outcomes monthly, but never manufacture precision. Useful measures include:

- external entries published and still correct;
- referral visits that reach installation or verification documentation;
- first-party package installs by registry and platform;
- successful `verify-claims` and onboarding journeys where voluntarily reported;
- independent reproductions and benchmark adapters accepted upstream;
- integration PRs contributed by users outside the core maintainer account;
- stale links, stale versions, rejected submissions, and unresolved packaging
  failures.

Do not merge download counts from unrelated packages or mirrors into one number
without a documented source and time window.

## Competitive claim policy

Allowed:

- factual, dated, linked differences in interfaces, installation, privacy,
  recovery, receipts, benchmark protocol, and supported surfaces;
- statements that Entroly provides a feature when the current release and docs
  verify it;
- workload-specific benchmark results with complete caveats.

Not allowed:

- "better than External Baseline" or "better than External Context Tool" without a named dimension and
  current neutral evidence;
- universal token, quality, cost, latency, or reliability claims;
- treating stars, downloads, launch votes, or list count as product quality;
- marking a third-party submission published before it is publicly visible.

## Definition of category leadership

Entroly reaches category-leading visibility when a qualified user searching for
context compression, context assurance, MCP context tools, Claude Code context,
AI-agent cost control, recoverable context, or evidence verification repeatedly
finds an accurate Entroly surface; can install it through their preferred
runtime; can verify its behavior locally; can inspect limitations; and can find
independent evidence under a fair protocol.

The repository, packages, documentation, external listings, reviews, benchmark
artifacts, and release announcements must all tell the same truthful story.
